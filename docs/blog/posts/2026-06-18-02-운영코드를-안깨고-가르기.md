# 운영 코드를 안 깨고 가르기 — 특성화 테스트 + parity로 동일성 증명

> 2026-06-18 · mint-agent 개발기 #02 · Phase 1(엔진/어댑터 경계 분리)
> **요약:** 운영 중인 코드를 리팩터하는데 테스트가 0개였다. "구조만 바꾸고 동작은 그대로"를
> 어떻게 *증명*하나? 특성화 테스트(golden master) + 원본 대조(parity)로 풀었다. 두 모듈을
> 모노레포로 이식했고, 28개 테스트가 통과하며 원본과 출력이 **완전히 동일**함을 확인했다.

---

## 문제 (Problem)

mint-agent의 핵심은 youtube-agent에서 **플랫폼 무관 엔진**을 뽑아내는 것이다. 그런데:

- youtube-agent는 **매일 스케줄러로 돌아가는 운영 코드**다. 깨면 안 된다.
- 그런데 **자동 테스트가 0개**였다.
- 리팩터의 절대 원칙은 "런타임 동작 불변"인데, **불변임을 무엇으로 보증하나?**

테스트 없이 구조를 바꾸는 건 눈 감고 운전하는 것과 같다. 먼저 안전벨트가 필요했다.

## 접근 (Approach)

네 가지 규칙을 세웠다:

1. **원본 무수정.** 운영 코드(`youtube-agent`)는 건드리지 않는다. 모듈을 **모노레포로 복사 이식**하고, 운영은 그대로 돌게 둔다.
2. **특성화 테스트 먼저.** 이식한 모듈의 *현재 동작*을 픽스처로 고정한다(golden master).
3. **원본 parity 대조.** 같은 입력을 원본과 이식본에 넣어 **출력이 글자 단위로 같은지** 확인 — "동일하다"를 주장이 아니라 증명으로.
4. **작은 조각부터.** 결정적(deterministic)이라 테스트가 깔끔한 모듈을 첫 타자로.

그리고 경계를 코드로 못 박았다 — `core`는 **결과 어휘만** 소유하고, 플랫폼 규칙은 **어댑터**가 소유한다. 둘의 접점이 `produce / review / publish` 계약이다.

## 결과 (Result)

**이식한 두 조각 (🟢 직접 검증):**

| 조각 | 모듈 | 성격 | 테스트 |
|---|---|---|---|
| `review` | `adapters/youtube/review.py` (compliance 게이트) | 룰 결정적 + LLM 폴백 | 특성화 10건 |
| `produce` | `adapters/youtube/captions.py` (타임라인→SRT 자막) | 완전 순수 | 특성화 18건 |
| 계약 골격 | `core/pipeline.py` (`PlatformAdapter`) + `core/trust/verify.py` (`Verdict`) | — | — |

- **`pytest` → 28 passed.**
- **원본 parity → IDENTICAL** (review 4/4 픽스처, captions cues 3/3 + SRT 내용 일치).
- 커밋: `1812102`(review) · `ca6dc41`(captions). youtube-agent 운영 코드 **무수정**.

parity 대조는 이렇게 간단하다 — 같은 입력, 두 구현, 결과 비교:

```python
import sys; sys.path.insert(0, r"...\youtube-agent")  # 원본
from agents.compliance import check as orig
from adapters.youtube.review import check as new

a = orig(script, seo, deep=False)
b = new(script, seo, deep=False)
assert a == b      # → IDENTICAL
```

## 배움 (Learnings)

**1. 특성화 테스트는 "맞아야 할 동작"이 아니라 "지금의 동작"을 고정한다.**
compliance 룰 전용 경로를 뜯어보니, high 위반이면 `passed=False`인데 `recommendation`은
`"reject"`가 아니라 `"review"`였다. 살짝 이상하다. 하지만 리팩터 단계에서 이걸 "고치면"
그건 더 이상 *동일성 보증*이 아니다. 그래서 테스트는 이 동작을 **그대로** 핀으로 박았다:

```python
def test_hard_block_high_fails_but_recommends_review():
    v = review(script_with_nsfw, seo, deep=False)
    assert v.passed is False
    assert v.recommendation == "review"   # 이상해 보여도 '현재' 동작
```

개선은 동일성을 증명한 *다음* 단계의 일이다. 리팩터와 동작 변경을 섞지 않는다.

**2. "동일하다"는 말로 하면 안 되고 증명해야 한다.** 내가 코드를 읽고 "같게 옮겼다"고
믿는 것과, 원본을 실제로 돌려 출력을 대조하는 건 다르다. parity 대조가 후자를 준다.

**3. 일반화는 미루는 게 용기다.** `Reviewer` 포트의 `review()` 시그니처를 지금 억지로
범용화하지 않았다 — 어댑터가 youtube 하나뿐인데 "모든 플랫폼"을 가정하면 틀린 추상이
박힌다. `core`가 공유하는 건 결과 어휘(`Verdict`)까지. 진짜 일반화는 **두 번째 어댑터가
강제할 때** 뽑는다. (브리프: "범위 폭주 금지.")

## 다음 (Next)

- 엔진 첫 조각(`memory`) 이식 — 어댑터에서 엔진으로 결합면 전환.
- 모델 호출 게이트웨이로 비용·관측 일원화(Phase 2 준비).

리듬이 자리잡았다 — **조각마다 테스트로 보호 + 원본 동일성 증명.** 이게 "데모"와
"운영 위에서 검증되는 리팩터"를 가르는 지점이다.
