# 추정에서 실측으로 — 정직한 계측의 완성

> 2026-07-06 · mint-agent 개발기 #09 · Phase 2(신뢰 레이어 1차)
> **요약:** [#06](2026-07-06-06-깔아둔-seam이-값을-하다-비용-라우터.md)의 비용 라우터는 토큰을
> *문자수로 근사*하고 "추정"이라 정직하게 표시했다. 이번에 그 근사를 **실측 usage**로 올리고,
> 쌓인 계측을 사람이 읽는 **관측 리포트**로 렌더링했다. 관통하는 원칙은 하나 — **계측은 정직해야
> 한다**: 확장은 하위호환으로, 실측이 없으면 근사로 폴백하되 그 차이를 라벨로 남기고, 리포트도
> 근사/실측·미가격·모순을 숨기지 않는다. 누적 테스트 355개 green.

---

## 문제 (Problem)

비용 라우터는 호출마다 (모델·토큰·비용)을 계측했지만, 토큰은 `len(text)/4` 문자수 근사였다.
`token_source`가 아직 없던 그때도 "이건 추정"이라 문서에 적었다. 이제 근사를 실측으로 올릴
차례인데, 세 가지 함정이 있었다:

- **`complete`는 `str`만 반환한다.** 어댑터 열 곳이 `gw.complete(...) → str`에 기대고 있다.
  usage를 얹겠다고 반환 타입을 바꾸면 이식 내내 지켜온 "어댑터 0줄 변경"이 깨진다.
- **provider가 usage를 항상 주는 건 아니다.** 응답에 usage가 없으면? 0으로 채우거나 폴백가로
  지어내면 — 이 프로젝트가 가장 경계하는 허구가 된다.
- **계측을 쌓기만 하면 죽은 데이터다.** `aggregate` dict는 기계용이다. 사람이 "그래서 비용이
  얼마고 게이트가 어떻게 굴러가나"를 한눈에 볼 무언가가 없다.

> **질문: 기존 계약을 안 깨고 실측을 더하되, 실측이 없을 때 지어내지 않고, 그 결과를 legible하게
> 보여주려면?**

## 접근 (Approach)

**① 하위호환 포트 확장 — `complete_ex`.** 기존 `complete → str`은 그대로 두고, usage까지 주는
새 메서드를 더한다. `complete`는 새 메서드에 위임한다.

```python
class UsageAwareGateway(Protocol):                    # 선택적 확장 포트
    def complete_ex(...) -> Completion: ...            # Completion(text, usage)

class GeminiGateway:
    def complete(self, ...) -> str:                    # 기존 계약 — 불변
        return self.complete_ex(...).text
    def complete_ex(self, ...) -> Completion:          # 실제 작업 + usage 추출
        ...
        usage = _usage_from(resp.usage_metadata, "prompt_token_count", "candidates_token_count")
        return Completion(text, usage)
```

어댑터는 여전히 `complete`로 `str`만 받는다(0줄 변경). 실측이 필요한 `CostRouter`만
`complete_ex`를 쓴다 — 그것도 게이트웨이가 `UsageAwareGateway`일 때만.

**② 없으면 근사, 근사는 근사라고 라벨한다.** provider가 usage를 안 주면 `Completion.usage=None`.
라우터는 그때 문자수 근사로 폴백하되, **어느 쪽인지 레코드에 남긴다**:

```python
if isinstance(self._gw, UsageAwareGateway):
    text, usage = ... complete_ex ...
if usage is not None:
    in_tok, out_tok, token_source = usage.input_tokens, usage.output_tokens, "measured"
else:
    in_tok, out_tok, token_source = estimate(...), estimate(...), "estimated"
```

`CallRecord.token_source`("measured" | "estimated")가 정직의 핵심이다 — 숫자만 보면 실측인지
근사인지 알 수 없으니, 그 출처를 데이터에 박아둔다.

**③ 리포트는 데이터보다 장밋빛이면 안 된다.** 쌓인 계측을 사람이 읽는 Markdown으로 렌더링하되,
정직성 표기를 그대로 옮긴다 — 실측/근사 비율·미가격 호출·모순 건수를 리포트에 명시한다.

```python
# core/observability.py — 실 운영 게이트 로그 36건을 렌더링한 실제 출력
## 발행 게이트 감사 리포트
- 통과율 2.8%
- 권고 reject=35 · review=1
- 합의 disagree=21 · consensus=15
- 모순 감사 7건 ⚠️ score_range=7        # 숨기지 않는다
```

## 결과 (Result)

**계측을 추정에서 실측으로, 그리고 리포트로 (🟢):**

| 조각 | 무엇 | 정직성 장치 | 커밋 |
|---|---|---|---|
| 실측 usage | `complete_ex` 포트 확장, 3 프로바이더 usage 추출 | 하위호환 + `token_source` 라벨 + 없으면 근사 | `53619af` |
| 관측 리포트 | 비용·게이트 계측 → Markdown 대시 | 실측/근사·미가격·모순을 리포트에 명시 | `94fff22` |

- **`pytest` → 355 passed** (이 두 조각에서 +21, 전부 실 API·네트워크 없이).
- **하위호환:** `complete`는 여전히 `str` 반환 — 어댑터·엔진 호출부 **0줄 변경**.
- **실 데이터 리포트:** 운영 게이트 로그 36건을 통과율·분포·모순 7건까지 legible한 리포트로 렌더.

## 배움 (Learnings)

**1. 확장은 계약을 깨지 말고 위임으로.** 새 능력(usage)이 필요할 때 기존 시그니처를 바꾸는 대신,
새 메서드를 더하고 옛 메서드가 그것에 위임하게 했다. 옛 계약은 불변, 새 능력은 옵트인. 열 곳의
호출부가 아무것도 모른 채 그대로 돈다 — 확장의 비용을 호출부에 전가하지 않는다.

**2. 정직은 '데이터의 출처'를 표시하는 것이다.** 실측이 없을 때 근사로 폴백하는 건 실용적이다.
문제는 그다음 — 근사를 실측인 척하면 거짓이 된다. `token_source`는 숫자 옆에 "이건 어디서 왔나"를
붙인다. 완벽한 실측을 기다리는 대신, *불완전함을 정직하게 표시*하고 지금 쓸 수 있게 한다.

**3. 리포트가 데이터보다 장밋빛이면, 그 리포트는 거짓말이다.** 모순 7건을 요약에서 빼면 통과율만
반짝인다. 관측의 목적은 예쁜 대시가 아니라 *진실을 legible하게* 만드는 것이다 — 나쁜 신호일수록
더 잘 보여야 한다.

**4. 신뢰 레이어는 스스로에게 먼저 정직해야 한다.** 남을 검증하는 레이어가 자기 계측을 부풀리면
자기모순이다. 근사를 근사라 하고, 없는 단가를 비우고, 모순을 노출하는 규율이 곧 신뢰 레이어의
자격이다.
