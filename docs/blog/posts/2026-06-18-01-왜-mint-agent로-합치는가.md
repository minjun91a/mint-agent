# 왜 youtube-agent와 trust-layer를 mint-agent로 합치나 — Phase 0

> 2026-06-18 · mint-agent 개발기 #01 · Phase 0(정리 & 결정)

## TL;DR

몇 달째 돌고 있는 YouTube 자동화(`youtube-agent`)와, AI가 사고 치지 않게 검사·관리하는
신뢰 레이어를 **하나의 엔진(mint-agent)** 으로 합치기로 했다. 첫날은 코드를 한 줄도 안 고치고
**현황 검증·결정·안전망·분류**만 했다. 그 과정에서 "내가 안다고 생각한 구조"와 "실제 코드"가
여러 군데 달랐고, git 안전망을 까는 과정에서 작은 실수도 했다. 그 기록.

---

## 1. 이번에 한 것

Phase 0의 목표는 코딩이 아니라 **출발선 정리**였다. 한 일은 넷:

1. **환경 검증** — 내 코드가 실제로 어디 있는지 확인.
2. **방향 결정 3가지 확정** — 레포 전략 / 안전망 / 두 번째 어댑터.
3. **git 안전망 구축** — 운영 중인 `youtube-agent`에 되돌리기 기준점 만들기.
4. **엔진/어댑터 분류표 작성** — [`docs/inventory.md`](../../inventory.md).

---

## 2. 왜 합치나

두 자산을 따로 두면 각각 약점이 분명하다:

- **youtube-agent 단독** → "콘텐츠 팜"으로 읽힐 위험. 자동으로 영상을 찍어내지만,
  AI가 가끔 없는 내용을 지어내고(환각) 비용·동작이 안 보인다.
- **신뢰 레이어 단독** → 사용자 0명짜리 데모웨어. 멋진 검증 로직인데 검증할 실트래픽이 없다.

**합치면 두 약점이 서로를 덮는다.** "실제로 돌아가는 시스템 위에서 검증되는 신뢰 레이어." 2026
채용 시장이 가장 강하게 거르는 게 *데모 vs 실제 운영*인데, 몇 달째 돌아가는 운영 증거는
대부분의 졸업생에게 없는 희소 자산이다. 거기에 신뢰 레이어를 얹으면 "프로덕션에서 버티는
관측 가능·비용 통제 시스템"이라는, 시장이 실제로 원하는 형태가 된다.

그래서 만드는 건 **플랫폼 독립적인 멀티 에이전트 엔진 + 신뢰 레이어**다. YouTube는 그 엔진이
결과물을 내보내는 **하나의 출구**일 뿐 — 진짜 자산은 엔진이다.

### 확정한 결정 3가지
| 결정 | 선택 | 이유 |
|---|---|---|
| 레포 전략 | 새 모노레포(`mint-agent`) | 깨끗한 경계로 시작, 운영 코드를 점진 이식 |
| 안전망 | youtube-agent에 git 먼저 | 리팩터 전 되돌리기 기준점 필수 |
| 2번째 어댑터 | research/digest | "지식워크 자동화"로 채용에 잘 읽힘 |

## 3. 막힌 것 / 배운 것

### 교훈 1 — "내가 안다고 생각한 구조"를 믿지 마라. 코드를 읽어라.

온보딩 문서는 루트를 `C:\MINT\`라고 적어뒀는데, 실제로는 코드가 **세 군데에 흩어져** 있었다:
- `C:\MINT-agent` — 모노레포(거의 비어 있음)
- `C:\Users\최민준\youtube-agent` — 진짜 운영 코드
- `C:\MINT` — 전혀 다른 워크스페이스

문서엔 `AGENT_REGISTRY`, `cleanup-execution-log.md` 같은 자산이 있다고 적혀 있었지만,
youtube-agent 코드엔 **그 이름의 파일이 없었다**. (전자는 홈 디렉터리의 *문서*였고, 후자가
말하던 "환각 라벨 데이터"의 실제 대응물은 `logs/compliance_audit_*.jsonl` 26개 파일이었다.)

> 문서는 과거의 스냅샷이다. 분류·결정은 문서가 아니라 **지금 코드**에 발맞춰야 한다.

### 교훈 2 — 가장 큰 발견: 결합면은 "하나"가 아니라 "셋"이었다.

"YouTube는 하나의 출구일 뿐"이라고 단순하게 생각했는데, 모듈 독스트링을 직접 읽어보니
실제 결합면은 셋이었다:

1. **Discord** — 컨트롤·승인(HITL)·알림 입출력
2. **YouTube** — 콘텐츠 출구
3. **AXIS** — 별도 비즈니스 자동화 시스템의 DB(`master_dashboard.db`)를 읽는 결합

엔진/어댑터를 깔끔히 나누는 진짜 난이도가 바로 여기 있다. 동시에 엔진의 *씨앗*(에이전트 코어,
채널 권한, 메모리, intent 라우터, 오케스트레이터)도 실재했다 — 다만 Gemini/Discord/youtube에
직접 결합돼 있어 "이미 분리됨"이 아니라 "추출이 필요함" 상태였다.

### 교훈 3 — 운영 코드에 git을 처음 깔 때, "커밋 전 검증"이 안전벨트다.

youtube-agent는 몇 달째 돌았는데 **버전관리가 없었다.** 리팩터하다 깨지면 되돌릴 수가 없으니
가장 먼저 git 스냅샷을 떴다. 그런데 여기서 실수를 했다.

비밀 파일과 352MB짜리 생성 미디어를 제외하려고 `.gitignore`에 이렇게 적었다:

```gitignore
output/             # 생성 미디어 352MB (재생성 가능)
.env.bak            # .env 백업 (시크릿)
```

**문제: `.gitignore`는 인라인 주석을 지원하지 않는다.** `output/  # ...` 전체가 하나의 패턴으로
해석돼서 아무것도 매칭하지 못했고, 결과적으로 `.env.bak`(시크릿 백업)과 `output/` 354MB가
전부 스테이징됐다. 다행히 **커밋 직전에 스테이징을 검사하는 게이트**를 둔 덕에 잡았다:

```bash
# 스테이징된 파일 중 비밀/대용량이 있으면 즉시 STOP
git diff --cached --name-only | grep -E '\.env|credentials/|\.pickle|^output/'
```

또 하나 배운 것: `.gitignore`는 **이미 인덱스에 추가된 파일에는 적용되지 않는다.** 패턴을
고쳐도 한 번 스테이징된 건 안 빠진다. 결국 인덱스를 통째로 비우고(`rm .git/index`) 고친
`.gitignore` 상태에서 처음부터 다시 스테이징해서 해결했다.

주석을 별도 줄로 옮기니 깔끔해졌다:

```gitignore
# 생성 미디어 352MB (재생성 가능)
output/
```

최종 스냅샷: **150개 파일, 1.4MB, 비밀 0건** (커밋 `705c0d3`). 시크릿·venv·output·로그·백업은
전부 제외하고 소스와 설정, 텍스트 eval 데이터만 담았다.

> 비가역적인 일(여기선 "비밀을 커밋에 박는 것")은 *실행 전에 검증하는 단계*를 끼워라.
> 자동화는 빠르게 틀리기 때문에, 게이트가 없으면 실수가 그대로 굳는다.

## 4. 다음 (Phase 1)

- **모노레포 골격** — `core/` · `adapters/youtube/` 와 `produce/review/publish` 인터페이스 정의.
- **3중 결합 분해** — Discord·YouTube·AXIS를 각각 어댑터로, `core/`는 인터페이스만 의존.
- **모델 호출 게이트웨이** — Gemini/OpenAI/Claude 직접 호출이 모듈마다 흩어져 있어서, 한 곳으로
  모으면 비용 라우팅과 관측성이 공짜로 따라온다.
- **선결 과제: 동작 동일성 테스트** — 리팩터 전후 산출물이 같음을 보증할 테스트가 아직 없다.
  구조를 바꾸기 전에 이걸 먼저 깔아야 한다.

핵심 원칙은 하나다 — **돌아가는 것을 먼저.** 일반화는 두 번째 어댑터가 강제할 때 추출한다.
