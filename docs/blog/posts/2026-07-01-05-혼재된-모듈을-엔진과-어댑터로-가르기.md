# 혼재된 모듈을 엔진과 어댑터로 가르기 — 라우터·페르소나·오케스트레이터

> 2026-07-01 · mint-agent 개발기 #05 · Phase 1(엔진/어댑터 경계 분리)
> **요약:** 순수하게 옮겨지던 모듈이 끝나고, "경계가 섞인" 세 모듈(control·persona·orchestrator)이
> 남았다. 셋 다 같은 원칙으로 갈랐다 — **메커니즘은 엔진, 어휘·정의는 어댑터, LLM은 게이트웨이,
> 외부 의존은 주입 seam, 범위 밖(AXIS)은 이식하며 제거.** 누적 테스트 235개 green.

---

## 문제 (Problem)

지금까지 옮긴 모듈은 대체로 "이건 엔진, 저건 어댑터"가 분명했다. 그런데 남은 셋은 [inventory](../../inventory.md)가
**"경계 혼재(境界混在)"** 라 이름 붙인 것들이었다:

- **control** — 라우팅 *메커니즘* + youtube intent *어휘* + 파이프라인 *배선*이 한 파일에.
- **persona** — 호출 *로직* + youtube 페르소나 *정의* + Discord 채널 *매핑* + 메모리 결합.
- **orchestrator** — 브리핑 *메커니즘* + **AXIS DB 수집** + youtube 수집이 뒤섞임.

> **폴더를 `core/`와 `adapters/`로 나누는 건 분리가 아니다. 무엇이 "플랫폼을 몰라도 되는 엔진"이고
> 무엇이 "youtube만의 것"인가?** 이 질문에 답하지 못하면 이름만 core인 코드가 된다.

## 접근 (Approach)

세 모듈을 **똑같은 절개선**으로 갈랐다. 반복되니 그게 이 프로젝트의 문법이 됐다:

1. **메커니즘 → 엔진(`core/`).** "story가 뭔지 모르는" 범용 라우터(`IntentRouter`), "어떤 페르소나인지
   모르는" 호출기(`PersonaRegistry`+`ask`), "무엇을 수집하는지 모르는" 브리퍼(`core/orchestrator`).
2. **어휘·정의 → 어댑터(`adapters/youtube/`).** 정규식 룰·intent 목록, 페르소나 프롬프트, youtube 수집기.
3. **LLM 호출 → 게이트웨이 재사용.** 세 모듈의 Gemini 호출을 전부 `core.llm` 게이트웨이로(프로바이더 무관).
4. **미이식·외부 의존 → 주입 seam.** 메모리는 `core/memory` 주입, `build_report`·`agent_runner`는 주입점,
   아직 못 옮기는 배선(control `dispatch`)은 막지 않고 **정직하게 보류**.
5. **범위 밖(AXIS) → 이식하며 제거.** orchestrator의 AXIS DB 수집부는 옮기지 않고, 프롬프트의 AXIS
   언급도 지운다. 그리고 **테스트로 부재를 강제**해 되살아나지 않게 못 박는다.

엔진이 정말 "플랫폼을 모르는가"는 말이 아니라 코드로 증명된다 — youtube가 아닌 토이 룰로도 도는지 본다:

```python
# 엔진 라우터는 youtube를 모른다 — 토이 룰만으로 라우팅된다
router = IntentRouter(
    [Rule(re.compile(r"add (\d+)"), "add",
          lambda t: {"n": int(re.search(r"add (\d+)", t).group(1))})],
    known_intents={"add", "unknown"},
)
assert router.parse("please add 7", allow_llm=False).args == {"n": 7}   # 'add'가 뭔지 몰라도 동작
```

그리고 "제거했다"는 주장도 테스트가 지킨다:

```python
# 이식하며 뺀 AXIS가 정말 사라졌는지 테스트가 강제 (되살리지 않는다)
for p in all_personas().values():
    assert "AXIS" not in p.system
# parity 확인: 원본 orchestrator의 AXIS 참조 8개 → 이식본 0개
```

## 결과 (Result)

**경계를 가른 세 모듈 (🟢):**

| 모듈 | 엔진(`core/`) | 어댑터(`adapters/youtube/`) | 주입/정리 | 커밋 |
|---|---|---|---|---|
| control | `IntentRouter`(룰+LLM 폴백) | intent 룰·어휘 | 게이트웨이 폴백 · `dispatch` 보류 | `5d63af7` |
| persona | `PersonaRegistry`·`ask` | 페르소나 정의·채널 매핑 | 메모리·게이트웨이·`agent_runner` 주입 | `d908385` |
| orchestrator | 수집→브리핑 메커니즘 | `collect_yt`·프롬프트 | `build_report` 주입 · **AXIS 제거** | `fc703e2` |

- **`pytest` → 235 passed** (이 트릴로지에서 183 → **+52**, 전부 실 LLM·DB 없이 도는 테스트).
- **원본 parity:** control 룰 경로 `Command` 수준으로 **IDENTICAL(15케이스)**, persona 구조(키·env맵) 동일.
- **AXIS 청소:** persona 2개 페르소나 → 0, orchestrator 참조 8 → 0. 코드가 아니라 **테스트가** 이 부재를 지킨다.

이 시점에 `core/` 엔진 골격이 찼다 — `llm · memory · pipeline · trust/verify · control · persona · orchestrator`.

## 배움 (Learnings)

**1. "분리됐다"는 엔진이 어댑터 없이도 말이 되는가로 증명된다.** 라우터가 youtube 룰이 아니라 `add (\d+)`
같은 토이 룰로도 돌면, 그건 진짜로 youtube를 모르는 것이다. 폴더 위치가 아니라 이 테스트가 경계를 증명한다.

**2. 같은 절개선이 세 번 반복되면 그게 프로젝트의 문법이다.** 메커니즘/어휘/게이트웨이/주입/청소 —
네 번째 모듈이 와도 "무엇이 플랫폼을 모르는 부분인가"만 물으면 어디를 자를지 바로 안다.

**3. 제거도 이식이다.** AXIS를 *안 옮기는 것*도 명시적 결정이었다. 지우고 끝내는 게 아니라, "AXIS 없음"을
검증하는 테스트를 남겨 미래의 나(또는 LLM)가 무심코 되살리지 못하게 했다.

**4. 못 옮기는 의존은 막지 말고 seam으로.** claude 러너·`build_report`·pipeline 배선은 아직 이식 전이다.
NotImplementedError로 막는 대신 주입점(`agent_runner`·`build_report`)을 파두면, 구조는 지금 완성하고 구현은
나중에 꽂는다. "지금 안 되는 것"을 정직하게 표시하되 설계는 멈추지 않는다.
