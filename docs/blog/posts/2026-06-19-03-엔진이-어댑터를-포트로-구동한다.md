# 엔진이 어댑터를 포트로 구동한다 — 추상화를 테스트로 증명

> 2026-06-19 · mint-agent 개발기 #03 · Phase 1(엔진/어댑터 경계 분리)
> **요약:** 모듈을 하나씩 옮겼지만 "정말 분리된 건가, 폴더만 나눈 건가?"는 증명되지 않았다.
> 엔진 발행 게이트를 *포트 타입으로만* 작성하고, youtube가 아닌 가짜 어댑터로도 그게 도는 걸
> 테스트로 보여 추상화가 실제로 작동함을 증명했다. 누적 테스트 58개 green.

---

## 문제 (Problem)

지난 편까지 `review`·`captions`·`clip_extractor`(어댑터)와 `memory`(엔진)를 모노레포로
옮겼다. 각각 테스트로 보호되고 원본과 동일함도 증명했다. 그런데 찜찜한 게 남았다:

> **"엔진이 어댑터를 진짜 *포트*로만 다루는가? 아니면 그냥 폴더만 `core/`와 `adapters/`로
> 나눠놓고 서로 직접 부르는가?"**

폴더를 나누는 건 분리가 아니다. 진짜 분리라면 **엔진이 어댑터의 구체 타입을 몰라야** 한다.
그걸 증명할 방법이 필요했다.

## 접근 (Approach)

1. **계약을 코드로 못 박았다.** `core/pipeline.py`에 `PlatformAdapter` 프로토콜
   (`produce / review / publish`)을 정의. 어댑터가 만족해야 할 인터페이스다.
2. **엔진 로직을 포트 타입으로만 작성했다.** 발행 게이트 `gate()`는 `PlatformAdapter`만
   받는다 — youtube를 import하지 않는다:

   ```python
   def gate(adapter: PlatformAdapter, content, seo) -> GateDecision:
       """엔진은 어댑터 구체 타입을 모른다 — 포트로만 다룬다.
       정책: approve만 진행, review(HITL 대기)·reject는 보류."""
       verdict = adapter.review(content, seo)
       return GateDecision(proceed=verdict.recommendation == "approve", verdict=verdict)
   ```
3. **youtube를 그 계약에 끼웠다.** `YouTubeAdapter`가 `PlatformAdapter`를 구현하고,
   `review`는 앞서 옮긴 compliance 게이트로 위임.
4. **분리를 증명하는 테스트를 짰다.** 핵심은 *youtube가 아닌* 가짜 어댑터로도 엔진 게이트가
   도는지 보는 것.

## 결과 (Result)

**지금까지 옮긴 것 (🟢):**

| 계층 | 모듈 | 상태 |
|---|---|---|
| 어댑터 | `review`(compliance) · `captions` · `clip_extractor` | 각 특성화 + 원본 parity |
| 엔진 | `core/memory`(ChannelMemory) | 특성화 + 원본 parity |
| 통합 | `YouTubeAdapter`(PlatformAdapter 구현) + 엔진 `gate()` | 통합 테스트 |

- **`pytest` → 58 passed.**
- 커밋: `daa0184`(clip) · `ffe346a`(memory) · `97c4e38`(AXIS 범위 제외) · `6a42dc6`(통합).

**추상화가 작동한다는 증거** — 엔진 게이트가 youtube와 *무관한* 가짜 어댑터에도 동일하게 동작:

```python
class _FakeAdapter:                       # youtube와 전혀 무관
    def __init__(self, verdict): self._v = verdict
    def produce(self, b): return b
    def review(self, c, s): return self._v
    def publish(self, a): return a

def test_gate_is_adapter_agnostic():
    approve = Verdict(passed=True, score=0.0, violations=[], recommendation="approve")
    reject  = Verdict(passed=False, score=1.0, violations=[Violation("x","high")], recommendation="reject")
    assert gate(_FakeAdapter(approve), {}, {}).proceed is True    # 엔진은 구체 타입을 모름
    assert gate(_FakeAdapter(reject),  {}, {}).proceed is False
```

엔진은 `_FakeAdapter`가 뭔지 모른다. 그저 `PlatformAdapter` 계약(=`review`가 `Verdict`를
돌려줌)만 믿고 동작한다. **이게 "분리됐다"의 증명이다.**

## 배움 (Learnings)

**1. "분리됐다"는 폴더가 아니라 폴리모피즘으로 증명된다.** `core/`와 `adapters/`로 나누는 건
누구나 한다. 진짜 분리의 증거는 *엔진이 다른 어댑터로도 도는가*다. 가짜 어댑터 테스트 한 줄이
"의도"를 "증명"으로 바꾼다.

**2. 엔진은 적게 알수록 강하다.** 엔진 게이트가 아는 건 `Verdict`의 `recommendation`뿐이다.
compliance 규칙이 정규식인지 LLM인지, youtube인지 아닌지 — 전혀 모른다. 적게 알기에 어떤
어댑터든 끼울 수 있다.

**3. 범위를 줄이는 것도 설계다.** 이번에 AXIS(외부 비즈니스 연동)를 프로젝트 범위에서
**의도적으로 제외**했다. 결합면을 셋에서 둘로 줄였다. "더 만드는 것"보다 "안 만드는 것"이
어려운데, 범위가 작아야 끝까지 간다(브리프: *돌아가는 것 먼저*).

**4. 가드레일은 엔진 레벨에 있어야 한다.** `gate()`는 `approve`만 통과시키고 `review`·`reject`는
보류한다 — Trust ②(HITL)를 엔진이 강제한다. 애매하면 멈추고 사람에게. 이 정책이 어댑터가
아니라 엔진에 있어서, 모든 플랫폼에 일관되게 적용된다.
